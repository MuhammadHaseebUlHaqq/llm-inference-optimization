Day 13  ·  Serving under an SLO: the Pareto, goodput, and preemption

Day 12 established the two ceilings. Day 13 is the question an interviewer actually asks: given those curves, what batch size do you ship? The answer is never "the one with the highest throughput", and being able to say why is the whole day.

13.1 Throughput and latency are one curve, not two

Every row of the sweep is a point on a Pareto frontier: decode throughput cannot be improved without paying per-token latency. Plotting one against the other collapses the whole table into the shape that matters.

Example 13-A: the Pareto frontier, RTX 3060, realistic pool 
 batch   TPOT ms   decode tok/s   tok/s per ms of TPOT
     1     11.28          88.6      7.9
    16     17.18         931.3     54.2
    32     21.35        1498.6     70.2
    48     23.25        2064.4     88.8
    64     23.73        2696.5    113.6   <- best ratio anywhere on the curve
    96     36.81        2608.0     70.9   <- throughput went DOWN, latency up 55%
   128     44.46        2879.0     64.8
   192     72.26        2657.1     36.8
   256     86.29        2966.7     34.4

the last column is throughput bought per unit of latency spent. it rises to
batch 64 and falls monotonically after. that is the knee stated as a ratio,
rather than eyeballed off a plot.

Note batch 96: throughput actually fell against batch 64 while TPOT rose 55%. That point is strictly dominated, meaning there is no SLO for which it is the right choice. A frontier with dominated points on it is normal and worth pointing out, because it shows the measurement had enough resolution to see non-monotonicity rather than smoothing it away.

13.2 Choosing a batch size, in the order you would actually do it

  1. Write the SLO first, as a TPOT budget and a TTFT budget. "p95 TPOT under 25 ms" is an SLO; "as fast as possible" is not.
  2. Find the largest batch that still meets the TPOT budget. At 25 ms on this card that is batch 64, at 23.73 ms, with 1.27 ms of margin.
  3. Check the TTFT budget separately, because it is the constraint that usually binds first.
  4. Check which ceiling is being hit, because the fix differs: more memory for an admission ceiling, a bigger or better-utilised card for a compute ceiling.
The TTFT trap. Step 2 alone gives batch 64. But TTFT at batch 64 is 5.516 s, against 0.112 s at batch 1: a 49x regression. If the SLO says "first token in under 2 seconds", the entire TPOT analysis is irrelevant and the answer is batch 16 (TTFT 1.404 s, decode 931 tok/s), which is 2.9x less throughput than the knee. Two SLOs, one curve, batch sizes a factor of four apart. This is the answer that separates someone who has run a sweep from someone who has read about one.

13.3 Goodput is the metric that stops you gaming throughput

Throughput counts every token emitted. Goodput counts only tokens belonging to requests that met their SLO. The distinction exists because throughput is trivially maximised by a policy that ruins latency for everyone, and the number still goes up.

Example 13-B: throughput up 10%, goodput to zero 
SLO: TPOT <= 25 ms.

batch  64:  TPOT 23.73 ms   decode 2696.5 tok/s   -> meets SLO
            goodput = 2696.5 tok/s   (every token counts)

batch 256:  TPOT 86.29 ms   decode 2966.7 tok/s   -> violates SLO by 3.5x
            throughput = 2966.7 tok/s   (+10%, and the dashboard is greener)
            goodput    = 0 tok/s        (not one request met its budget)

the operator who optimises the first number ships batch 256, and every user
sees a 3.5x slower stream. the goodput column is what makes that visible.

13.4 Preemption: what a paged engine does when the pool runs out

The constrained-pool run from Day 12 was a scheduler experiment as much as a memory one. With a pool holding 25 concurrent sequences, batch 32 does not fail and does not thrash. It queues.

constrained pool: 1224 blocks x 16 tokens = 19,584 tokens = 25 sequences

 batch   TPOT ms   decode tok/s   queued
    16     17.07          937.3   False
    32     33.18          964.5   TRUE     <- flips at the first batch above 25
    48     43.92         1093.0   TRUE
    64     67.38          949.8   TRUE

Two mechanisms are available to a paged engine when admission fails, and they are worth naming separately:

  • Swapping. Copy a victim sequence's KV blocks out to host memory, and bring them back when it is rescheduled. Costs PCIe bandwidth twice, and preserves the computed KV.
  • Recomputation. Drop the victim's blocks entirely and re-run its prefill on resume. Costs compute, needs no transfer. Cheaper than swapping whenever prefill is fast relative to the link, which on this card it is: prefill runs at 4205 tok/s.

Both are why the constrained curve degrades gracefully to about 1000 tok/s rather than collapsing. Contrast the HuggingFace baseline, which under the same memory pressure does not queue, does not swap, and does not recompute: it raises OutOfMemoryError and the process dies. That is the same contrast as the OOM experiment, seen from the scheduler's side instead of the allocator's.

13.5 The cross-GPU control: is the knee a property of the model or of the card?

This is the most defensible part of the batching work, because it was a stated prediction that was then tested on different hardware.

The prediction: the knee is where the per-sequence marginal cost catches the shared weight read. The weight read is a property of the model, so the knee should sit at roughly the same batch size on a different card, even though every absolute number moves.

What the control proved, and what it refuted. Confirmed: the knee location is a model property. It stayed at 64 on a card with 2.6x the bandwidth. Refuted: the plateau prediction. I predicted 6000-7000 tok/s on the 3090 from the bandwidth ratio alone and measured 10,112. Bandwidth was the wrong single axis, because the plateau is set by a skinny GEMM whose ceiling the 3090's extra compute also lifts. Say both halves. A prediction that half-failed and was diagnosed is a stronger signal than one that succeeded.

13.6 Why the plateau is not either roofline

The natural assumption is that a plateau means a hardware ceiling. Check it in numbers, on the 3060 at batch 256:

compute:    ~9 TFLOPS achieved   of ~51 TFLOPS peak    = 16%
bandwidth:  ~90 GB/s achieved    of 360 GB/s peak      = 25%

neither is saturated, and throughput still will not rise.

The reason is operation shape. Batched decode is a GEMM with M = batch, which stays skinny even at 256 against a K and N in the thousands. A skinny GEMM is occupancy-bound rather than FLOP-bound, and tops out well under tensor-core peak. Meanwhile the paged KV reads are scattered across blocks, so they do not reach streaming bandwidth either. The plateau is the ceiling of those specific kernels, not of the GPU.

The naive roofline agrees on the shape and fails on the number: it predicts an ideal batch of 142 at fp32-accumulate peak, or 280 at fp16-accumulate peak, against a measured 64. That 2x-to-4x gap is itself a finding, and it is the honest form of the roofline claim. The roofline tells you which regime you are in, not what number you will hit.

13.7 Self-test, Day 13

Q1. Your sweep says batch 256 is fastest. Do you ship it?
No. It is 10% more decode throughput than batch 64 for 3.6x the per-token latency, and against a 25 ms TPOT SLO its goodput is zero while batch 64's is 2696 tok/s. I would ship 64, and if TTFT is also budgeted I would ship lower still: TTFT at 64 is 5.5 s against 0.11 s at batch 1.

Q2. How do you know your knee is not an artifact of that one GPU?
I reran the sweep on an RTX 3090 with 2.6x the bandwidth and 1.4x the compute. TPOT stayed flat through batch 64 and broke at 96 on both cards, so the knee did not move, which is what the T_fixed + c1 x batch model predicts, because the fixed term is the model's weight read. The plateau height did move, 2967 to 10,112 tok/s, and my bandwidth-only prediction of 6-7k was wrong for a reason I can name: the second card also lifts the skinny-GEMM ceiling.

Q3. Your throughput flattened. Which resource ran out?
On this card, none of them. At batch 256 I was at 16% of compute peak and 25% of bandwidth peak. The limit is kernel shape: decode is a skinny GEMM that is occupancy-bound, plus scattered paged KV reads. That is also why the knee is at 64 and not at the roofline's predicted 142.

Day 15  ·  Quantization, part 1: the argument, in bytes

Quantization is a differentiator topic rather than a guaranteed one, and the goal for these two days is one paragraph of mechanism per method plus one measured result that is genuinely your own. Day 15 builds the argument from the roofline. Day 16 does the methods, and then the result that contradicts the argument.

15.1 Why quantization helps inference at all

Start where Day 5 ended. A batch-1 decode step reads all 3.09 GB of fp16 weights to produce a single token, and does about 2 x 1.54e9 = 3.1 GFLOP of arithmetic doing it. That is an arithmetic intensity near 1 FLOP/byte, against a ridge point of 142. The step is nowhere near the compute ceiling and is entirely a memory-traffic problem.

So the lever is bytes. If the same computation can be driven from weights stored in 4 bits instead of 16, the dominant term in the step shrinks by 4x, and per-token latency should follow.

Example 15-A: the ideal bandwidth floor at each width 
weights = 1,543,714,304 params

fp16   2 bytes/param  = 3.087 GB  -> 3.087 / 291.5 GB/s = 10.6 ms/token  ( 94 tok/s)
int8   1 byte /param  = 1.544 GB  -> 1.544 / 291.5      =  5.3 ms/token  (189 tok/s)
int4   0.5 byte/param = 0.772 GB  -> 0.772 / 291.5      =  2.6 ms/token  (378 tok/s)

291.5 GB/s is the MEASURED achievable read bandwidth on this card,
not the 360 GB/s spec figure. quoting the spec figure inflates every
line above by 23%.
The sentence to have ready. "Weight-only quantization is a bandwidth play, not a compute play. At batch 1 the arithmetic intensity is about 1 against a ridge of 142, so I am paying for bytes moved and not for FLOPs done. Halving the bytes is the whole mechanism, and it follows that the win shrinks as batch size grows, because batching amortises the same weight read over more tokens and moves the step toward the compute-bound side."

15.2 The corollary that most people miss

If quantization wins by shrinking a shared read, then its benefit is largest exactly where that read is least amortised: batch 1. At batch 64, the same 3.09 GB is already being spread across 64 tokens, so the weight term is 64x less important per token and the step has moved toward the skinny-GEMM ceiling from Day 13. This is checkable against the measured numbers.

batch  1:  T_fixed ~ 11 ms   is essentially ALL of the 11.28 ms step
batch 64:  T_fixed ~ 11 ms   is 11 of a 23.73 ms step, so ~46%
           the other ~54% is c1 x 64 = 12.7 ms of per-sequence work

halving the weight bytes attacks T_fixed only:
  batch  1:  11.28 -> ~5.8 ms    (about 1.9x faster)
  batch 64:  23.73 -> ~18.2 ms   (about 1.3x faster)

Same optimization, very different payoff, and the reason is a decomposition already measured. That is the kind of answer that shows a model rather than a memorised fact.

15.4 The dequantization tax, stated before you meet it

A 4-bit weight is not something an Ampere tensor core can multiply. sm_86 has no int4 or fp8 tensor path that a general GEMM can use here, so the actual execution is:

for each weight tile:
    read 4-bit packed values from HBM        <- the saving, real
    look up / scale them back into fp16      <- the tax, per element
    feed fp16 tensor cores                   <- unchanged arithmetic

The read shrinks by 4x. The arithmetic does not shrink at all, and a dequantization step is added that did not exist before. Whether this is a win depends entirely on whether the step was actually bottlenecked on that read. Hold that thought: it is exactly what the measurement on Day 16 tests, and it is exactly where the measurement goes against the story.

15.5 Formats, precisely enough to be challenged on

FormatBitsWhat it is
fp16161 sign, 5 exponent, 10 mantissa. The baseline of record here.
bf16161 sign, 8 exponent, 7 mantissa. Same range as fp32, less precision. Not used in this repo, deliberately, for comparability with V100 and T4 runs later.

Why NF4 rather than plain int4. Quantization error is minimised by putting your 16 available codes where the mass of the distribution is. Trained weights are roughly zero-mean Gaussian, so NF4 spaces its levels at the quantiles of a normal, making the codes information- theoretically optimal for that assumption. Combined with block-wise scaling (a separate scale per 64 weights, so one outlier cannot flatten a whole tensor) and double quantization (quantizing those scales too), that is the QLoRA recipe.

Day 16  ·  Quantization, part 2: the methods, and the run that got slower

16.1 The four methods, one paragraph of mechanism each

MethodThe mechanism, in one sentenceWhat it is really solving
GPTQQuantize weights one column at a time and, after each one, update the remaining unquantized columns to compensate for the error just introduced, using second-order (Hessian) information from a small calibration set.Rounding error is not independent across weights. Greedy per-weight rounding compounds; error-compensating rounding does not.
AWQObserve that a small fraction of weight channels (about 1%) matter far more for output quality, identify them from activation magnitudes rather than weight magnitudes, and scale those channels up before quantizing so they land on a finer part of the grid. Not all weights are equally important, and importance is visible in the activations, not in the weights themselves.
SmoothQuantActivations have huge outliers and weights do not, which makes W8A8 fail on the activation side. The organising observation across all four: the hard part of quantization is not the rounding, it is the outliers. GPTQ compensates for their error, AWQ protects them, SmoothQuant relocates them, LLM.int8() isolates them. Four answers to one problem is a much better framing than four unrelated acronyms.

16.2 KV-cache quantization, which is a different lever entirely

Weight quantization shrinks a fixed cost. KV quantization shrinks a growing one, which matters on exactly the axis the OOM experiment measured.

analytical KV at fp16      = 28 KiB/token
analytical KV at int8      = 14 KiB/token

at the measured slope of 62 KiB/token, weights+KV filled 12GB at 123,565 tokens.
halving only the KV term does not halve the slope, because the measured slope
includes HuggingFace's double-copy: peak is weights + 2 x KV, not weights + KV.
which is the useful point: a paged engine gets the full benefit, a torch.cat
loop gets the benefit twice over on a term that should never have doubled.

The interview version: KV quantization is the one quantization lever whose payoff scales with context length and batch size, so it is the one that matters for long-context serving, while weight quantization is the one that matters for batch-1 latency and for fitting the model at all.

The trap question, and it will be asked. "You just told me weight-only quantization is a bandwidth play. Your 4-bit run reads 2.68x fewer weight bytes. Why did it get 2.27x slower?" Anyone who has only read about quantization stalls here. The answer is in this repo's own profiling data.

16.4 The answer, in three steps

Step 1: the bandwidth win is real, and it is not the bottleneck. The fp16 HuggingFace decode step is 62.3% device idle and fires 1198 kernels per token. It was never running at the bandwidth ceiling; it reached only 15-20% MBU. An optimization that reduces bytes read cannot help a step that is not waiting on bytes read. It is Amdahl's law applied to the wrong term.

fp16 decode, HF:   35.51 ms/token, of which ~62% is device idle
                   -> ~13.4 ms of actual device work
                   3.087 GB / 13.4 ms = 230 GB/s ... but that is the BUSY
                   window only. across the whole step it is 87 GB/s, ~24% of
                   the 360 GB/s spec figure. bytes were never the constraint.

Step 2: dequantization adds work to a step that was already launch-bound. Every quantized linear layer now runs a dequantize kernel before its GEMM. That is more kernels and more launches per token, on a loop where 62.3% of the time was already dispatch overhead. The optimization made the dominant term worse.

effective bandwidth achieved, whole step:
  fp16:  3.087 GB / 35.51 ms  =  86.9 GB/s
  NF4:   1.152 GB / 80.52 ms  =  14.3 GB/s

the NF4 run moves 2.68x fewer bytes in 2.27x more time. the extra
45.0 ms/token is not memory traffic at all. it is dequantization plus
the launches that carry it.

Step 3: the caveat that makes the answer correct rather than merely defensive. This measures this implementation on this card. bitsandbytes NF4 dequantizes to fp16 and calls an fp16 GEMM, and sm_86 has no int4 tensor-core path to skip that with. A serving stack with fused dequantize-and-matmul kernels, such as Marlin or an AWQ or GPTQ kernel in vLLM, folds the dequantization into the GEMM's prologue and does realise the bandwidth win. The result here is correct and specific, not a claim that 4-bit quantization is useless.

16.5 What the run did buy, quantified

The memory result is the real win and it converts directly into the other headline experiment.

weights freed = 2945.29 - 1099.13 = 1846.16 MiB

at the MEASURED OOM slope of 62 KiB/token:
    1846.16 MiB x 1024 / 62 KiB = 30,489 more tokens of context

at the ANALYTICAL 28 KiB/token (what a paged engine would actually see):
    1846.16 x 1024 / 28        = 67,511 more tokens of context

so on the same 12GB card, NF4 moves the OOM cliff from 123,565 tokens to
roughly 154,000 in the HF loop. it buys context, not speed.
The complete answer, as one paragraph. "Weight-only quantization is a bandwidth play, so I expected 4-bit to be faster at batch 1. It was 2.27x slower. The reason is that my baseline was not bandwidth-bound: profiling showed the HF decode step was 62.3% device idle across 1198 kernel launches, running at under a quarter of peak bandwidth. Shrinking the bytes attacks a term that was not binding, while dequantization adds kernels to the term that was. It is bitsandbytes-specific and card-specific, because sm_86 has no int4 tensor path, so the dequantize is a separate step rather than a fused GEMM prologue. What the run did buy is memory: 1846 MiB of weights freed, which is about 30,000 more tokens of context at my measured KV slope. Quantization bought me context, not latency, and the profiler explains exactly why."

16.6 Self-test, Days 15-16

Q1. Why does quantization help inference more than it helps training?
Inference at low batch is memory-bound with arithmetic intensity near 1 against a ridge of 142, so the cost is bytes moved and weights are the largest static tenant. Training is compute-bound, has a backward pass and optimizer state, and needs gradient precision. Quantization attacks the term that dominates inference and not the one that dominates training.

Q2. Would you expect a bigger or smaller win from quantization at batch 64 than at batch 1?
Smaller. The weight read is T_fixed, about 11 ms, and it is essentially the entire 11.28 ms step at batch 1 but only about 46% of the 23.73 ms step at batch 64, because c1 x batch has grown to 12.7 ms. Halving the weight bytes gives roughly 1.9x at batch 1 and roughly 1.3x at batch 64, on my own decomposition.

Q3. GPTQ and AWQ both do 4-bit weight-only. What is actually different?
GPTQ is error compensation: quantize column by column and update the not-yet-quantized columns with Hessian information so the accumulated error is corrected. AWQ is error avoidance: find the roughly 1% of channels that matter, identified from activation magnitudes rather than weight magnitudes, and scale them so they land on a finer part of the grid. One repairs the damage, the other steers around it.

Q4. Your 4-bit run got slower. Does that mean quantization does not work?
No, it means my baseline was not bandwidth-bound and my kernel was not fused. The step was 62.3% idle across 1198 launches, so cutting bytes could not help, and bitsandbytes NF4 dequantizes into a separate fp16 GEMM because sm_86 has no int4 tensor path. A fused dequantize-and-matmul kernel such as Marlin on a stack that is actually bandwidth-bound is the configuration where the win appears. I measured one point precisely, and I can say exactly which of its assumptions to change.
